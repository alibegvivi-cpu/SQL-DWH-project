## 🌎 Общие принципы

* **Стиль написания:** Всегда используйте стиль **`snake_case`** (строчные буквы, слова разделяются нижним подчеркиванием `_`).
* **Язык:** Исключительно английский язык для всех объектов базы данных.
* **Зарезервированные слова:** Запрещено использовать зарезервированные ключевые слова SQL (такие как `select`, `table`, `date`, `user`) в качестве названий объектов.

## 🗂️ Правила именования таблиц

### Слой Bronze
Все названия таблиц должны начинаться с имени исходной системы. Имя сущности должно строго соответствовать оригинальному названию таблицы в источнике без переименования.
```text
<sourcesystem>_
```
* `<sourcesystem>` — имя системы-источника (например, `crm`, `erp`).
* `` — точное имя таблицы в исходной системе.
* **Пример:** `crm_customer_info` ➔ Сырые данные о клиентах из CRM-системы.

### Слой Silver
В слое очистки структура названий сохраняет связь с источником, подтверждая, что данные прошли базовую валидацию и дедупликацию, но все еще привязаны к конкретному бизнес-приложению.
```text
<sourcesystem>_
```
* `<sourcesystem>` — имя системы-источника (например, `crm`, `erp`).
* `` — имя сущности.
* **Пример:** `crm_customer_info` ➔ Очищенные и типизированные данные о клиентах из CRM.

### Слой Gold
В Золотом слое используются осмысленные, понятные бизнесу имена таблиц, которые начинаются со специального префикса категории.
```text
<category>_
```
* `<category>` — описывает роль таблицы: измерение (`dim`) или таблица фактов (`fact`).
* `` — описательное имя таблицы, соответствующее бизнес-домену (например, `customers`, `products`, `sales`).

#### Глоссарий паттернов категорий

| Паттерн | Назначение / Описание | Примеры |
| :--- | :--- | :--- |
| **`dim_`** | Таблица измерений (Dimension table) | `dim_customers`, `dim_products` |
| **`fact_`** | Таблица фактов (Fact table) | `fact_sales` |
| **`report_`**| Аналитическая витрина / Отчет (Report/View) | `report_customers`, `report_sales_monthly` |

## 📊 Правила именования колонок

### Суррогатные ключи
Все первичные ключи в таблицах измерений должны использовать обязательный суффикс `_key`.
```text
<table_name>_key
```
* `<table_name>` — имя таблицы или сущности, к которой относится данный ключ.
* `_key` — суффикс, явно указывающий, что колонка является суррогатным ключом DWH.
* **Пример:** `customer_key` ➔ Суррогатный ключ в таблице измерений `dim_customers`.

### Технические колонки
Все системные метаданные и технические колонки DWH должны начинаться с префикса `dwh_`, за которым следует понятное описание назначения поля.
```text
dwh_<column_name>
```
* `dwh_` — префикс, зарезервированный исключительно для сгенерированных системой метаданных.
* `<column_name>` — описание технической метрики.
* **Пример:** `dwh_load_date` ➔ Техническое поле для хранения даты и времени загрузки записи в хранилище.

## ⚙️ Хранимые процедуры (Stored Procedures)

Все хранимые процедуры, отвечающие за загрузку, трансформацию и оркестрацию данных, должны строиться по следующему шаблону:
```text
load_<layer>
```
* `<layer>` — целевой слой данных, в который осуществляется загрузка (`bronze`, `silver` или `gold`).
* **Примеры:**
  * `load_bronze` ➔ Хранимая процедура для извлечения данных из файлов и их посадки в Бронзовый слой.
  * `load_silver` ➔ Процедура для очистки и трансформации данных при перекладывании в Серебряный слой.
